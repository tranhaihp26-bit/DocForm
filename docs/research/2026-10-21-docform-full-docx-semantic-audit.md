# DocForm local: audit and design for full DOCX, visual evidence and semantic rules

Date: 2026-10-21. Scope: the Antigravity DocForm local checkout only. ONLYOFFICE is outside this design. This is a read-only code and document audit plus an implementation specification; no live OAuth, AI upload, browser acceptance, Word rendering or automated tests were performed for this report.

## Objective and exact meaning

For each imported DOCX, preserve the original bytes; have the local parser and an AI reader independently inspect the same source; give the AI both machine-readable file content and rendered pages; reconcile their findings by source location; approve only defensible matches; route uncertainty to the user; and only then select and apply formatting rules to confirmed semantic units in Body and each Appendix.

“Full DOCX to AI” means original file bytes cross the AI service boundary after a new, file-specific consent. “Visual reading” additionally requires a rendition of every relevant page. A DOCX upload alone does not provide visual layout to a model: OpenAI's Responses file-input documentation says non-PDF documents yield text only, whereas vision-capable PDF input yields text and page images. Code Interpreter can process DOCX but is a separate tool capability. The present ChatGPT-plan DevKit adapter accepts text messages only. These Platform features must not be assumed to be available through the current plan/OAuth adapter.

**Added user requirement:** The full-file path must actually submit the untouched original DOCX as a file input, rather than concatenate extracted text or relabel the existing block batches as a file upload. The AI must also inspect a locally rendered, source-bound visual representation of the entire document and produce separate evidence for file/text, code/structure and page/layout reading. The application must state which of these happened; transfer success alone is not evidence that every page or OOXML feature was understood. This requirement applies to DocForm local, not the ONLYOFFICE plugin.

## Audit snapshot and evidence

- Checkout: `main`, HEAD `450de41` at audit time; 157 modified/untracked paths. This is a moving, dirty working tree. Freeze a fresh manifest before implementation; neither this HEAD nor historical test claims are acceptance evidence for later changes.
- User-supplied biên bản source: 39,308 bytes, SHA-256 `912578d9d8dba01d4aa3d8326db885c410b582b0c7ad519a54465c2831adc53b`; 38 direct `w:p` and 2 direct `w:tbl` children of `w:body` in `word/document.xml`; no `word/media` part, comment part, tracked-change tags, header or footer XML in this particular file. These package facts do not establish correct reading or pagination. It contains no appendix fixture for acceptance of the new Appendix behavior.
- `src/utils/localFileImport.ts` reads bytes in the browser, computes a hash, extracts blocks and stores the immutable source with `saveSourceBlob`; `src/utils/draftStore.ts` verifies the stored hash and separates `source_blobs` from draft autosaves.
- `src/server/blockExtractor.ts` extracts ordered paragraph/table blocks and table geometry. `src/server/structuralSegmenter.ts` maps a whole block to one of eight `SourceRegion` values. Its Appendix path starts at heading-like paragraphs, marks all following blocks `appendix`, and currently sets `extractionStatus: "confirmed"` at creation. That status is extraction bookkeeping, not evidence of user confirmation.
- `src/shared/schemas/document.schema.ts` has block IDs, source paths, table data/models and field provenance. It has no durable Body/Appendix semantic subtype, hierarchy or per-unit approval. `src/utils/workspaceState.ts` has `EditableNode` with lineage and a partition approval, but the approval covers coarse region/cell mapping, not semantic meaning within Body/Appendix.
- `src/canonical/bodyOoxmlEvidence.ts` distinguishes a few paragraph roles for measurement. `src/canonical/bodyRuleApplicability.ts` selects broad paragraph/table eligibility. `src/canonical/ruleEngine.ts` has rule statuses including `NEEDS_REVIEW` and `NOT_APPLICABLE`; none of these form an approved, source-linked semantic graph for the full Body and each Appendix.
- `src/shared/partitionAiProtocol.ts` strips blocks to ID/index/kind/text/cell text and location. `src/server/aiPartitionService.ts` batches 25 blocks. `src/server/chatgptPlanProvider.ts` calls a vendored DevKit `streamResponse` with a text prompt. `docs/SIWC_LOCAL.md` correctly states that original bytes, HTML/XML and page images are not sent by the current path. The separate document-review prompt truncates raw text to 15,000 characters.
- `src/utils/workspaceTransactions.ts` and `src/utils/exportCandidate.ts` provide reversible edits, coarse approval, candidate fingerprinting, table/media safety gates. They are reuse points; candidate identity and byte equality do not prove semantic or visual correctness.

## Findings and severity

| ID | Finding | Consequence | Design response |
| --- | --- | --- | --- |
| F1 | Current ChatGPT-plan adapter is text-only. | Full DOCX, hosted code execution and page vision are unavailable on this path. | Capability probe using synthetic content; fail closed with a clear `unavailable` status. Do not silently switch account/provider or claim visual review. |
| F2 | DOCX input alone is text-only in the documented Responses file path. | Layout, images, spacing and page breaks may be invisible to AI. | Render the same source bytes to PDF/page images using a named engine, bind each rendition to source SHA and renderer/version, and inspect every page. |
| F3 | Existing AI and parser outputs cannot be compared at semantic unit level. | `40/40 blocks reviewed` measures coverage, not agreement or correctness. | Add typed independent observations, a reconciler, explicit per-unit decisions and source-linked evidence. |
| F4 | Body is one coarse region, and Appendix extraction is coarse. | A heading, meeting vote, ordinary paragraph and table cell can receive the wrong rule. | Add logical semantic subunits and parent/child relations without altering physical source blocks. |
| F5 | Current partition approval does not cover semantic subtype or formatting intent. | Rules or export may treat an uncertain interpretation as confirmed. | Version semantic approvals separately and include their fingerprint in rule/candidate gates. |
| F6 | Agreement can be a shared mistake; page-image interpretation is approximate. | Blind auto-approval can certify a false label or wrong geometry. | Auto-approve only deterministic low-risk matches with exact source evidence; route high-impact/ambiguous cases to the user. Geometry is measured in OOXML/rendition, not accepted solely from AI coordinates. |
| F7 | In the supplied metadata-step screenshot, no document-type card is selected. `ImportStepView.tsx` disables **Xem tóm tắt** whenever `doc.documentType` is empty. | The user reaches a disabled action despite the source file and recognition result being present; the next required action is easy to miss. | Show the required selection beside the action, offer a source-evidenced **Biên bản** suggestion for explicit confirmation, and explain any regime/source conflict. Check pointer and keyboard reachability in the real UI; the screenshot/code audit alone does not prove an interaction defect. |
| F8 | The ability to send a file using a general Responses API credential does not establish that the personal ChatGPT-plan OAuth connection permits file input, images or hosted tools. | A local multipart endpoint could misleadingly show “file sent” while only forwarding extracted text, or rely on an unauthorized token route. | Separate browser→local byte receipt, local→AI original-file transfer, provider file-read acknowledgement, code-read evidence and every-page visual evidence. Probe the exact OAuth path with synthetic data; expose capability and outcome per stage. |

## Target data contract

1. Keep `SourceManifest` and original bytes immutable. Add a `FullFileTransferRecord` containing source SHA/generation, consent ID, provider, documented transport, submitted MIME/byte count, provider request/file reference when safely available, transfer status and expiry/retention information; it records what was actually sent, without copying bytes into the draft. Add a `VisualEvidenceManifest` containing source SHA, renderer and version, page count, per-page hashes, render status and optional PDF/page-image references. A partial or failed render is explicit; it cannot become `visually_reviewed`.
2. Add a semantic annotation layer to the working snapshot, separate from `SourceBlock.role` and editable HTML. A unit has stable logical ID; scope `body` or `appendix`; `appendixId` when relevant; `parentUnitId`; label; source block/cell IDs and ordered text range or OOXML path; exact quote/hash; local evidence; AI evidence; optional page reference; confidence; decision and decision revision. Splitting one physical paragraph into several logical units must retain one-to-many lineage; tables retain physical `tableId`/`cellId` and span geometry.
3. Labels are hierarchical and document-type aware. Shared Body labels: section/heading, legal basis, lead, narrative, list, article/clause/point, table header/data, note, figure/unsupported and unknown. Biên bản adds meeting time/place, participants, chair/secretary, agenda, discussion, opinion, vote, conclusion, assignment and closing. Appendix labels: number/title, parent-document reference, section/heading, explanation, list, table header/data, note/source, media/unsupported and unknown. Do not force the biên bản taxonomy onto other document types.
4. `ParserObservation` and `AiObservation` are independent records over the same source SHA, not one model shown the other's answer. AI may receive stable source anchors and a page index, but not parser-assigned roles or draft labels in its first pass. An alignment stage then maps AI quotes/page findings onto source IDs. Missing, duplicated and uncertain alignments stay unresolved.
5. `ReconciliationDecision` is `auto_confirmed`, `user_confirmed`, `needs_review`, `rejected` or `unsupported`. Auto-confirm requires matching source identity, canonical label, scope, appendix boundary, parent relationship, exact quote and cell/range anchor, with deterministic corroboration. Regime, document type, signature/recipient identity, appendix boundary, mixed/merged table ownership and any unsupported rich content remain manual or blocked even if two readers agree.
6. `RuleSelection` records `ruleId`, regime, document type, profile, semantic unit ID, evidence and applicability result. Only confirmed units are eligible for mutation; other units receive `NEEDS_REVIEW` or `NOT_APPLICABLE` with a reason. Style/aesthetic suggestions remain distinct from legal requirements.
7. Any source change, regime switch, changed partition, split/merge, appendix move or edit affecting an anchored unit invalidates dependent observation/approval/rule evidence. Candidate fingerprint includes semantic decisions and visual manifest identity. Unsupported content remains readonly or blocks transformed export; original download remains available.

## User flow and consent

1. Import source locally, show hash/storage status, choose/confirm regime, and obtain a local structural extraction.
2. After the selected OAuth path is proven to support each required input, show a separate **Send full DOCX and rendered pages to selected AI** consent with original file name, SHA/size, renderer/page count, provider, data classes and documented persistence/deletion behavior. Previous text-only consent does not authorize this wider transfer. Never run the full-file request merely because the user opened a preview. An unavailable capability disables the action and explains the reason.
3. Display independent local and AI observations side by side, each with original-source quote and page/OOXML evidence. Show one decision per disputed unit, plus bulk acceptance only for a defensible set with a visible count and reversible history.
4. Apply applicable rules only after semantic approval. The user can inspect rule source, target, expected formatting, proposed delta and preview before accepting a formatting change.
5. Export from one approved candidate revision. Preview, OOXML checks, downloaded DOCX and print must share its bytes/SHA. Compare original and candidate page renderings for layout-sensitive changes, while keeping native Word/visual acceptance a separate status.

## Capability gate and fallback policy

The user selected personal/local ChatGPT plan, without an OpenAI Platform API key. The present vendored DevKit's `StreamResponseOptions.input` is `string | ResponseInputMessage[]` with string message content, and its implementation sends text-only content. The next work must first determine, using official documentation and a synthetic native probe, whether this exact OAuth scope/account/SDK path can accept original-file input, page-vision input and code tools. Probe and report these independently: `original_file_transfer`, `provider_file_read`, `code_read`, `all_page_visual_review`. A text response saying “I read the file” is insufficient evidence. No custom token bypass or unverified API request should be treated as supported. If a capability is unavailable, retain the local parser/semantic-review improvements, mark that capability `UNAVAILABLE`, and do not claim the complete workflow. A separate billed Platform account/provider would require a new user product decision and is outside this plan-only constraint.

## Acceptance matrix to build during implementation

- Representative NĐ30 and HD05 documents; biên bản plus documents with 0, 1 and multiple appendices; tables with merged/nested cells, repeat header, long text and page splits; a draft lacking signatures; body text that mentions `Điều` or `Căn cứ` without being an article/legal basis; association `BAN CHẤP HÀNH` with national header; unsupported drawing/image; split/merge edits and stale AI replies.
- Separate statuses and evidence for local OOXML extraction, AI code/file review, page-vision coverage, source alignment, semantic agreement, user approval, rule applicability, candidate OOXML fidelity, preview and native Word/PDF inspection. `PASS` in one column cannot fill another.
- The supplied biên bản is a useful real-data read-only case for title/regime and Body semantics, but has no appendix. Use synthetic or properly authorized appendix fixtures for that part; never copy sensitive source text into fixtures, logs or prompts in the repository.
